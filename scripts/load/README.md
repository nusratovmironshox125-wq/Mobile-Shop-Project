# Генератор нагрузки

Этот набор работает только с отдельным тестовым магазином. Он не даёт готового заключения о 1000/2000 посетителях. Короткий локальный запуск проверяет генератор, фикстуру и сверку сохранённых заявок. Полные испытания требуют отдельного сервера и отдельного генератора; рабочую БД владельца использовать нельзя.

## Проверенный локальный сценарий

Из корня проекта в PowerShell с JDK 21:

    powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-local.ps1 -LoadSmoke

Можно добавить -ReuseBuild только для уже проверенного актуального JAR: сборка и Java-тесты в таком запуске НЕ выполняются. Опциональный -BackupFile проверяет приватную резервную копию в другой тестовой БД. Локальный сценарий использует PostgreSQL 127.0.0.1:55432, rms_test и rms_load, порты приложения 18080/18081; процессы останавливаются в finally.

seed.sql требует пустую rms_load, создаёт 10000 моделей, 20000 вариантов, 40000 метаданных изображений и 100000 заявок без рабочих контактов. Реальных фото нет: это API-профиль, не тест изображений/CDN. prepare-accounts.mjs создаёт девять тестовых ADMIN и использует тестового OWNER. Приватный файл учётных данных удаляется после локального запуска.

check-load-smoke.ps1 запускает open 20 основных запросов/с, 2 с разогрева, 10 с измерения, 10 пользовательских форм и 10 администраторов. Доля POST мала: короткий запуск может получить слишком мало заявок для процентилей. reconcile.mjs сверяет каждый подтверждённый номер и Idempotency-Key с PostgreSQL. Ошибки и 429 не отбрасываются.

## Полный стенд — ещё не выполнено

1. Развернуть приложение из чистого checkout, PostgreSQL и согласованный reverse proxy/edge. Применить миграции к отдельной пустой rms_load, затем seed.sql. Проверить маркер магазина RMS LOAD ONLY и отключённый Telegram. На рабочий магазин этот маркер не устанавливать.
2. Подготовить десять выделенных тестовых сотрудников с изменёнными временными паролями, включая одного OWNER. Файл JSON содержит массив объектов login/password; хранить вне Git с ограниченными правами. prepare-accounts.mjs намеренно ограничен локальным тестовым портом; внешние учётные записи готовит оператор стенда.
3. Установить Node.js 22+ на отдельном генераторе. Секреты передаются только путём к локальному файлу. Зафиксировать commit, CPU/RAM/диск/сеть всех узлов, Java/PG, JVM/DB/pool/cache/edge, метрики CPU/GC/DB waits и синхронизацию времени.
4. Для разрешённого стенда задать переменные и запустить из корня проекта:

    $env:RMS_LOAD_ALLOW = 'owned-test-environment'
    $env:LOAD_ORIGIN = 'https://адрес-тестового-стенда'
    $env:LOAD_ADMINS_FILE = 'C:\private\accounts.load-credentials.json'
    $env:LOAD_OUTPUT = 'C:\private\results\closed-1000'
    $env:LOAD_MODE = 'closed'
    $env:LOAD_CLIENTS = '1000'
    $env:LOAD_RPS = '100'
    $env:LOAD_WARMUP_SECONDS = '600'
    $env:LOAD_SECONDS = '1800'
    node scripts/load/run.mjs

Папка результатов должна существовать. closed моделирует действия раз в 8–12 секунд; фактический RPS берётся из отчёта. open использует LOAD_RPS независимо от времени ответа и учитывает dropped при исчерпании генератора. Дополнительно работают десять администраторов, поэтому общий HTTP RPS выше предложенного основного RPS. Подготовка форм идёт до разогрева с интервалом 180 мс. При простое формы CSRF обновляется перед POST; эти дополнительные запросы учитываются в измерениях.

Повторить отдельно open/100 RPS/1800 с, closed/2000/3600 с, open/200 RPS/1800 с; затем closed/1000/14400 с, скачок 500→2000, холодный кеш, общий NAT и ступени выше 2000 по основному ТЗ. Для отдельных запусков использовать разные LOAD_OUTPUT. Ступенчатый сценарий пока требует оркестрации оператором; run.mjs сам пользователей по времени не меняет.

При общем NAT проверить production-потолки источника и персональные ограничения, не отключая защиту. Не подставлять произвольный X-Forwarded-For ради обхода лимита. Ошибки таймаута/сессии/429 должны входить в итоговый результат. Поведение генератора на длительном профиле ещё не проверено.

## Результаты

- .ndjson — каждый измеренный HTTP-запрос: тип, статус, длительность, время, без cookie/контактов.
- .json — предложенная нагрузка, достигнутый RPS, ошибки/429/dropped и p50/p95/p99 каждого типа.
- .receipts.json — подтверждённые синтетические номера/ключи для сверки с БД.
- .plans.json — EXPLAIN ANALYZE BUFFERS для каталога/поиска на локальной фикстуре.
- .reconciliation.json — результат сверки подтверждённых заявок локального smoke.

query-plans.mjs и reconcile.mjs намеренно ограничены локальной rms_load. На внешнем стенде оператор выполняет аналогичную сверку: каждый подтверждённый ключ соответствует ровно одной записи с тем же номером; отсутствие потерь и дублей нельзя заключить только из HTTP 201. Снять метрики сервера, WAF и браузера отдельно, приложить исходные результаты. Цели и фактические измерения — в ../../docs/PERFORMANCE_REPORT.md.
