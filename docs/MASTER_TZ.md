1. Цель и границы продукта
Создать быстрый адаптивный сайт магазина телефонов и, при включённой категории, ноутбуков. Посетитель изучает каталог, ищет модель, фильтрует товары по цене, сохраняет понравившиеся товары и оставляет заявку с именем и телефоном. Сотрудник магазина получает заявку с выбранным товаром и связывается с клиентом самостоятельно.

На сайте нет онлайн-оплаты. Рассрочка представлена информацией о доступности и условиях; финансовое оформление происходит вне сайта. Заявка не является оплатой, подтверждением продажи или резервированием остатков.

Ожидаемое распределение устройств: 65–70% телефоны, остальные — ноутбуки/компьютеры. Это предположение заказчика; после запуска его проверяют агрегированной статистикой без сбора лишних персональных данных.

Администратор звонит клиенту и меняет статус заявки.
4. Функциональные требования каталога
FR-01. Главная и навигация
В шапке: изменяемое название магазина, ссылки на включённые категории, скидки, контакты, избранное, выбор языка и темы. На телефоне допустимо компактное меню; поиск должен быть легко доступен.

Карточка содержит фото, название модели, цену или «от …», кнопку избранного и, при наличии, короткую отметку скидки/рассрочки. Полные характеристики на главной не выводить. Не добавлять тяжёлый рекламный слайдер по умолчанию.

Изменение названия отражается в шапке, подвале, заголовках сайта и уведомлениях. Нельзя задавать пустое название; максимум 100 символов.

FR-02. Поиск, фильтрация и сортировка
Поиск по бренду и названию модели без учёта регистра; обрезать лишние пробелы, ограничить строку 100 символами.
Цена «от/до» включительно; неотрицательные значения; нижняя граница не выше верхней.
Сортировка: по актуальной цене вверх/вниз, по новизне. Для одинаковых значений использовать стабильный дополнительный порядок по ID.
Фильтры и сортировка совместимы, сохраняются в URL. Кнопка «Сбросить» очищает их.
Поиск после паузы ввода около 300 мс; отменять/игнорировать устаревшие запросы, чтобы поздний ответ не заменял более новый.
Размер страницы — строго 10 моделей. API page от 0, другое целочисленное size нормализуется к 10. totalElements и totalPages считают модели после фильтров. Это правило также действует для административных списков и избранного; ограниченный список ID избранного допускает локальную пагинацию.
Если ничего не найдено, показать понятное сообщение и сброс фильтров, без ошибки сервера.
Расширенные технические фильтры не обязательны для v1. Не добавлять их без изменения объёма работ.
Для модели с несколькими комплектациями в выдачу попадает модель, у которой хотя бы одна опубликованная доступная комплектация удовлетворяет фильтру. Показывать минимальную цену именно среди подходящих комплектаций. Переход из выдачи открывает подходящую комплектацию; состояние фильтра не должно приводить к вводящей в заблуждение цене.

FR-03. Категории
Стартовые категории: телефоны и ноутбуки. ADMIN может менять название, порядок, видимость, добавлять категорию общего типа. Для телефонов и ноутбуков используются соответствующие схемы характеристик; добавление нового технического типа требует расширения схемы.

Скрытие категории убирает её из навигации, поиска и публичного каталога вместе с товарами. Данные не удаляются. Прямые публичные URL скрытых товаров возвращают 404; заявки на них не принимаются. В админ-панели всё остаётся доступно. При обратном включении ранее опубликованные товары возвращаются.

FR-04. Товары и комплектации
Модель и продаваемая комплектация — разные сущности. У каждой комплектации уникальный стабильный артикул/SKU, своя цена, наличие, цвет, память и другие отличающиеся параметры. SKU не переиспользовать для другого товара.

Общие данные модели: категория, бренд, название, slug, описание, фотографии и тип характеристик. Состояния публикации: DRAFT, PUBLISHED, ARCHIVED. Наличие комплектации: IN_STOCK или OUT_OF_STOCK. Автоматический складской учёт не требуется.

Телефон: цвет, RAM при применимости, память, экран, процессор, камеры, аккумулятор, SIM/eSIM, ОС, прочие параметры. Ноутбук: цвет, CPU, GPU, RAM, накопитель, экран, ОС, вес, прочие параметры. Данные, которые различаются у комплектаций, хранить на уровне комплектации; не допускать расхождения общей карточки и выбранного варианта. Неизвестные характеристики не выдумывать, пустые строки в публичной карточке скрывать.

Чтобы опубликовать модель, обязательны название, категория, бренд, хотя бы одна корректная комплектация и фотография. Для комплектации обязательны SKU, положительная цена и наличие. Публикация при OUT_OF_STOCK допустима, но отправка заявки на неё отключена с пояснением.

Физическое удаление разрешено только для черновика без связанной истории. Использованные в заявках товары архивировать. Исторические заявки и снимки данных сохраняются.

FR-05. Цена и скидки
Денежные суммы хранить точно через Java BigDecimal и PostgreSQL numeric, не float/double. Рабочая цена положительна. При скидке обычная цена выше акционной. Возможны начало/окончание скидки; отсутствие окончания означает бессрочную скидку до ручного отключения.

Единое правило расчёта действующей цены использовать в каталоге, товаре и заявке. Время хранить в UTC, показывать администратору в Asia/Tashkent. Границы акции: начало включительно, окончание исключительно. Просроченная скидка не показывается активной даже при задержке фоновых процессов.

Раздел скидок содержит модели хотя бы с одной доступной комплектацией с действующей скидкой. Показываемая старая и новая цена принадлежат одной комплектации. Если акция касается только одной памяти/цвета, это явно видно. Формат сумм понятный, например «3 500 000 сум».

FR-06. Рассрочка
Для комплектации: доступность рассрочки и необязательное текстовое описание условий. Не генерировать автоматически ежемесячный платёж, проценты или условия, которых не указал магазин. На карточке достаточно отметки; внутри товара — подробности. Заявка не означает одобрение рассрочки.

FR-07. Страница товара
Последовательность: фото → модель и выбранная комплектация → цена/наличие/скидка/рассрочка → описание и характеристики → «Оставить заявку» → телефон и адрес магазина. На мобильном допустима дополнительная закреплённая кнопка, если она не закрывает контент и поля.

При смене комплектации обновляются SKU, цена, наличие, условия и соответствующие фото. Не допускать невозможного сочетания параметров. Обе кнопки заявки, если их две, работают с одним текущим выбором.

FR-08. Избранное
Работает без аккаунта, хранится в текущем браузере, до 100 моделей. Сохранять только идентификаторы, не персональные данные. Состояние сохраняется после перезагрузки, синхронизируется между вкладками; очистка браузера удаляет список, другие устройства его не получают.

Актуальные цены и наличие получать с сервера. Для архива/скрытого товара показать нейтральное «Товар недоступен» с удалением из списка без раскрытия скрытых данных. При недоступном хранилище браузера использовать временное хранение и понятное предупреждение. Никакие ошибки избранного не должны ломать каталог.

FR-09. Контакты и настройки магазина
Поля: название, основной телефон, Telegram username/URL, адрес, ориентир/описание проезда, координаты и/или безопасная ссылка на карту; часы работы — необязательное поле.

Телефон открывает tel:, Telegram — проверенную HTTPS-ссылку t.me, карта — валидированную ссылку разрешённого провайдера. Не разрешать произвольный HTML/iframe и опасные URL-схемы. Встроенная карта необязательна: ссылка «Открыть на карте» обеспечивает нужную функцию и не замедляет первый экран.

Настройки имеют единый источник: обновление отражается на странице контактов, в подвале и под заявкой. Открытые клиентские страницы могут обновляться при следующем запросе/перезагрузке; новое значение должно становиться доступным через публичный API не позднее 60 секунд после сохранения.

FR-10. Язык и тема
Русский и узбекский на латинице: меню, настройки, кнопки, фильтры, статусы, подписи полей, валидация, ошибки и системные подтверждения, включая админ-панель. Тексты моделей, характеристик, описания, ориентиров и рассрочки показываются в том виде, в котором их ввёл администратор; автоматический перевод не требуется.

Первый язык — по поддерживаемой локали браузера, иначе русский. Тема сначала по системе, затем явный выбор пользователя. Выбор сохраняется в браузере. Переключение не сбрасывает фильтры, выбранную комплектацию или введённую заявку. Исключить заметное мерцание неправильной темы при загрузке.

5. Заявки и уведомления
FR-11. Форма заявки
Поля: имя 2–80 символов, телефон, выбранная комплектация (видимый контекст, не свободное текстовое поле), ознакомление с информацией об обработке данных. Поддерживать Unicode-имена с пробелами, дефисами и апострофами; не ограничивать имя только русскими/латинскими буквами.

По умолчанию телефон Узбекистана с +998, допускается вставка пробелов/скобок. Backend нормализует и проверяет номер. Для международных номеров использовать корректный формат E.164 и проверку библиотеки, если код страны разрешён настройками; не принимать произвольную строку. SMS-подтверждение в v1 отсутствует, поэтому номер считается указанным клиентом, а не подтверждённым.

Клиент передаёт ID комплектации и ключ повторной отправки, но не является источником цены, SKU или названия. Сервер повторно проверяет публикацию, категорию, наличие и цену. Если цена изменилась после открытия формы, вернуть 409 с актуальными данными и предложить повторное подтверждение; не создавать заявку молча по другой цене.

При сохранении зафиксировать: публичный номер заявки, имя, нормализованный телефон, ID модели/комплектации, SKU, название, выбранные параметры, цену и валюту, сведения о скидке/рассрочке на момент заявки, дату, статус, версию текста информирования. Хранить только необходимые персональные данные.

Защита от дубля: Idempotency-Key на одну попытку; повтор с тем же ключом и телом возвращает прежний результат, с другим телом — 409. Сохранять ключ не менее 24 часов и не раскрывать по нему персональные данные. Нажатие кнопки несколько раз не создаёт несколько заявок. Дополнительный антиспам не должен запрещать законный новый заказ навсегда.

Ответ об успехе только после commit в PostgreSQL. При потере связи после отправки браузер может повторить запрос с прежним ключом. При ошибке базы не показывать успех. После успеха очищать имя/телефон из формы и не сохранять их в localStorage.

FR-12. Обработка заявок
Список: номер, дата, имя, телефон, товар/SKU, комплектация, цена, статус. Поиск по номеру заявки, SKU, телефону; фильтры статуса и даты; пагинация. Карточка заявки показывает исторический снимок, даже если товар позже изменён или скрыт.

Статусы: NEW → CONTACTED → COMPLETED либо CANCELLED; разрешена отмена NEW. COMPLETED означает завершённую обработку по отметке сотрудника, а не подтверждение банковской оплаты. Повторное открытие конечной заявки доступно OWNER с причиной; история сохраняется. Внутренний комментарий до 2 000 символов.

Изменение статуса/комментария записывает автора и время. При одновременном редактировании использовать optimistic locking и 409, не затирать изменение другого администратора.

Новая заявка появляется в панели при следующем обновлении, не позднее 15 секунд при обычной работе. Допустим polling только при открытой видимой вкладке с остановкой при выходе; WebSocket не обязателен.

FR-13. Уведомления
Админ-панель — основной источник заявок. Telegram-уведомление подключается настройками окружения и подтверждённым ID получателя/группы. Токен не отдаётся frontend и не хранится в репозитории. Настройка публичного Telegram магазина не является настройкой получателя клиентских данных.

Сообщение: название магазина, номер заявки, имя, телефон, товар, комплектация, SKU, цена, дата. При ссылке на заявку всё равно требуется вход администратора. Экранировать имена и названия для выбранного формата сообщения.

Надёжная доставка: в одной транзакции сохранить заявку и запись outbox. Встроенная фоновая задача Spring отправляет уведомление после commit, с ограниченными таймаутами и числом параллельных отправок. Внешний брокер не требуется. При нескольких экземплярах backend захват записей должен исключать одновременную обработку и иметь срок аренды для восстановления после сбоя.

Повторы с задержками, например 1, 5, 15, 60 минут, затем через 6 часов; учитывать ограничения Telegram. После исчерпания попыток статус FAILED, предупреждение OWNER и ручной повтор. Ошибка Telegram не отменяет заявку и не задерживает HTTP-ответ клиенту.

При исправном подключении цель — 95% уведомлений отправлены в течение 60 секунд. После сбоя возможна повторная доставка одного сообщения: обещать exactly-once внешнего сообщения нельзя. Номер заявки позволяет распознать дубль; сама заявка остаётся единственной.

Без настроенного Telegram система показывает OWNER «Уведомления не подключены» и не имитирует отправку. Создавать интеграционные тесты с заглушкой провайдера, а реальный тест выполнять только с явно заданным тестовым получателем.

6. Управление администраторами
FR-14. Учётные записи
OWNER видит имя, логин, роль, ACTIVE/DISABLED, дату создания, время последнего входа. Пароли и их хеши не показываются. Создание ADMIN — уникальный логин, имя и одноразовый временный пароль с обязательной заменой при первом входе. Временный пароль показать один раз, не писать в лог; доставка вне сайта остаётся владельцу.

Отключение/смена пароля немедленно отзывает активные сессии. ADMIN не меняет роль через подмену тела запроса. Удаление учётной записи с историей заменяется отключением; аудит не исчезает.

В v1 нет публичного восстановления пароля по телефону. OWNER может сбросить пароль ADMIN с отзывом сессий. Восстановление OWNER — документированная административная процедура с доступом к серверу, без универсального аварийного пароля.

FR-15. Аудит
Фиксировать входы/неудачные попытки в ограниченном объёме, создание/отключение администраторов, изменение настроек, публикацию/архивирование, цены/скидки, статусы заявок, восстановление доступа. Поля: actorId, действие, объект/ID, время UTC, безопасное описание изменений, correlationId.

Не записывать токены, пароли, cookie, полные тела заявок и телефоны в технические логи. Просмотр полных клиентских данных только через защищённые API. Доступ к аудиту только OWNER; никто не редактирует аудит через обычный интерфейс.

7. Интерфейс, адаптивность и доступность
UX-01. Визуальное направление
Классический современный магазин: аккуратная сетка, нейтральный фон, один основной акцент, читаемая типографика, ровные изображения. Темы имеют одинаковую структуру. Финальные логотип/цвет выбираются на этапе дизайна; рабочее название «Real Mobil Shop» изменяемо.

Сначала спроектировать 360–430 px, затем планшеты и desktop. Проверить 320, 360, 390, 768, 1024, 1440 px. На телефоне обычно две карточки в ряд, на самых узких экранах одна; число определяется читаемостью. Нет горизонтальной прокрутки страницы и перекрытия кнопок системной клавиатурой.

UX-02. Доступность
Основные интерактивные цели не меньше 44×44 CSS px.
Семантические элементы, подписи полей, alt изображений, видимый keyboard focus.
Доступность меню, модального окна и формы с клавиатуры; возврат фокуса после закрытия.
Контраст обычного текста минимум 4.5:1, крупного текста/важных элементов по применимым критериям WCAG AA.
Ошибки понятны текстом, не только цветом; не показывать пользователю stack trace.
Статусы загрузки, пустого результата, отсутствия фото, отсутствия сети и ошибки API.
Размеры изображений зарезервированы заранее, чтобы карточки не прыгали.
Поддержка увеличения текста/масштаба; анимации минимальны и учитывают reduced motion.
UX-03. Матрица устройств
На дату выпуска проверить последние две стабильные основные версии Chrome, Edge, Firefox; Safari на macOS/iOS и Chrome на Android. Автоматизированный WebKit не заменяет полностью проверку настоящего Safari. Записать фактически проверенные версии и модели устройств; недоступные проверки отметить как не выполненные.

8. Архитектура и стек
8.1. Общая схема
Браузер обращается к одному HTTPS-домену. CDN/WAF защищает публичный вход, reverse proxy отдаёт статический React frontend и маршрутизирует /api в Spring Boot. PostgreSQL и административные порты недоступны из интернета. Фото хранятся вне БД в управляемом файловом/объектном хранилище и раздаются через защищённый публичный контур.

Слой	Решение
Frontend	React, TypeScript, Vite, маршрутизация, RU/UZ словари, обычный CSS/CSS Modules
Backend	Java, Spring Boot, Spring MVC, Bean Validation
Авторизация	Spring Security, серверные сессии и cookie
Данные	Spring Data JPA + Hibernate + PostgreSQL
Миграции	Flyway, одна последовательная история схемы
Сборка	Существующий Maven/Gradle wrapper; не менять без причины
Интеграция	Java HTTP-клиент, outbox в PostgreSQL, встроенная фоновая отправка
Эксплуатация	Reverse proxy, HTTPS, CDN/WAF, метрики и резервное копирование
Node.js используется для установки frontend-зависимостей и сборки; production бизнес-API полностью Java. Redis, Elasticsearch и отдельные сервисы добавлять только после измерения проблемы и архитектурного решения.

8.2. Backend: один Spring Boot проект со слоистой архитектурой
По уточнению заказчика основная структура организуется по техническим слоям: config, controller, service, repository, entity, dto. Предметные части каталога, цен, заявок, уведомлений, настроек, доступа, аудита и медиа можно выделять подпакетами внутри слоёв, когда это улучшает читаемость. Не заменять понятную структуру чрезмерно сложной архитектурой.

Корневой Java package сохранять из существующего проекта, если он корректен. Если проекта ещё нет, предложенный вариант — uz.nusratov.realmobilshop. Класс RealMobilShopApplication размещается в корневом пакете над остальными, чтобы component/entity/repository scanning работал предсказуемо. Полное имя приложения и существующие ссылки не переименовывать без проверки.

Пакет	Ответственность и примеры
config	Конфигурация приложения: SecurityConfig, настройки HTTP-клиента, типизированные properties
controller	HTTP-маршруты и DTO: ProductController, LeadController; административные endpoints можно вынести в controller.admin
service	Бизнес-сценарии, транзакции и правила: ProductService, LeadService, PricingService
repository	Интерфейсы Spring Data JPA, запросы и спецификации; ProductRepository, LeadRepository
entity	JPA-сущности и связи: Product, ProductVariant, Lead, AdminUser
dto	Отдельные входные/выходные модели: CreateLeadRequest, ProductResponse; допустимы подпакеты request, response
mapper	Явное преобразование entity/DTO, без HTTP и запросов к БД
exception	Предметные исключения и единый GlobalExceptionHandler
security	Аутентификация, текущий пользователь, проверки доступа; конфигурация фильтров остаётся в config
integration.telegram	Реализация внешней отправки через Telegram; не содержит управление заявками
scheduler	Запуск обработки outbox/служебных задач; делегирует работу сервисам
Дополнительные пакеты создавать только по фактической необходимости. Enum размещать рядом с соответствующим предметным кодом или в выделенном пакете с понятным назначением; не складывать все классы в utils/`common`. Не создавать пустые слои и интерфейсы только ради количества файлов.

Поток запроса: controller принимает и валидирует DTO → service проверяет правила и права, выполняет транзакцию → repository обращается к PostgreSQL через JPA/Hibernate → результат преобразуется в response DTO. Controller не обращается к repository напрямую. Entity не возвращается напрямую через API. Mapper не загружает ленивые связи скрытыми запросами и не меняет данные.

Транзакции обозначать на сервисном уровне и ограничивать работой с данными; не включать ожидание Telegram или загрузку внешнего URL. Все поля валидируются на сервере. Публичные и административные API имеют явное разделение. Использовать constructor injection, без field injection и статического доступа к ApplicationContext.

src/main/resources содержит конфигурации без секретов и db/migration; тестовые пакеты зеркалят основной код. Frontend находится в отдельном каталоге проекта и не смешивается с Java-пакетами. Существующие Maven/Gradle и source roots сохраняются, если изменение не требуется для работоспособности.

8.2.1. Проверяемые правила SOLID
Принцип	Как применять в этом проекте
S — одна ответственность	Controller обрабатывает HTTP, сервис — бизнес-сценарий, repository — доступ к данным. LeadService не форматирует Telegram-сообщение и не содержит HTTP-клиент провайдера
O — расширение поведения	Для уведомлений/хранилища использовать узкий контракт на границе; другой канал добавляется отдельной реализацией без переписывания сохранения заявки
L — корректная замена реализации	Реализация контракта сохраняет его смысл: одинаковая обработка успеха/ошибки, без неожиданной потери заявки или изменения цены; покрыть тестом адаптера/контракта
I — небольшие интерфейсы	Не делать универсальный ShopService с десятками несвязанных методов; контракты определяются нуждами потребителя
D — зависимость от абстракций	Бизнес-код не создаёт напрямую Telegram HTTP-клиент; adapter внедряется через интерфейс. Репозитории внедряются как интерфейсы Spring Data
Не требовать SomeService + SomeServiceImpl для каждого простого сервиса с одной реализацией. Интерфейс обязателен там, где есть реальная внешняя граница или варианты поведения; простые сервисы могут оставаться конкретными классами. Наследование не использовать ради устранения пары одинаковых строк, когда достаточно композиции.

Архитектурная проверка должна ловить зависимость controller → repository, зависимость entity → controller/HTTP DTO, обход границы уведомлений и публичную сериализацию entity. Допустим ArchUnit или эквивалентная проверка плюс ревью реальных сценариев; тесты не должны закреплять случайные имена классов. Существующий код реорганизовать небольшими изменениями с регрессией, а не удалять и писать заново.

8.3. Совместимость и существующий проект
На этапе M0 определить версии JDK, Spring Boot, сборщика и PostgreSQL по проекту и окружению. Выбрать поддерживаемую стабильную совместимую комбинацию, зафиксировать версии и lockfile. Не применять snapshot и не обновлять проект целиком только ради «самой новой» версии. При отсутствии ограничений ориентироваться на поддерживаемый LTS JDK, совместимый с выбранным Spring Boot.

Windows-разработку поддерживать через понятные PowerShell-команды с кавычками вокруг путей. Docker не является обязательным условием локального запуска. Тестовая PostgreSQL должна быть отдельной от пользовательской базы; контейнеры допустимы как необязательный способ изоляции, если доступны.

8.4. Подтверждённые владельцем параметры локальной БД
Для запуска на Windows-компьютере владельца использовать существующую PostgreSQL:

Параметр	Значение
JDBC URL	jdbc:postgresql://localhost:5432/real_mobil_shop_sayt?currentSchema=public
Host / port	localhost:5432 на компьютере владельца
Database / schema	real_mobil_shop_sayt / public
Локальный username	postgres
JDBC driver	org.postgresql.Driver
Пароль	Предоставлен владельцем для локальной настройки; в этом ТЗ не сохраняется
Текущая настройка владельца включает spring.jpa.show-sql=true и spring.jpa.hibernate.ddl-auto=update. Это сведения об исходной конфигурации, а не основание автоматически изменять существующую схему. SQL в консоли полезен для локальной отладки; логирование значений параметров с персональными данными включать нельзя. Для production show-sql=false, версия схемы управляется Flyway и проверяется Hibernate.

Безопасный шаблон после подготовки миграций, профиль local:

spring.datasource.url=jdbc:postgresql://localhost:5432/real_mobil_shop_sayt?currentSchema=public
spring.datasource.username=postgres
spring.datasource.password=${DB_PASSWORD}
spring.datasource.driver-class-name=org.postgresql.Driver
spring.jpa.show-sql=true
spring.jpa.hibernate.ddl-auto=validate
DB_PASSWORD задаётся в локальном окружении/Run Configuration IntelliJ, не в коммите или этом документе. Не менять пароль самостоятельно без причины. Для production задать отдельного пользователя с минимальными правами и отдельные секреты; локальный postgres не копировать в production как рабочую роль.

Первое обследование должно быть read-only и по возможности не запускать приложение с DDL auto-update. До готовности согласованных миграций допустим диагностический запуск с ddl-auto=none и отключённым Flyway, если это нужно для безопасной проверки существующей схемы. validate не создаёт отсутствующие таблицы: сначала корректные миграции, затем проверка. Не включать одновременно два конкурирующих механизма изменения схемы. Не выставлять baseline-on-migrate=true вслепую для существующей БД — сначала сравнить схему и определить корректную исходную версию.

Не переключать локальное приложение на H2, другую PostgreSQL, Docker-базу или облачный сервер ради успешного запуска без явного объяснения и согласованного решения. Если прежний исполнитель использовал другую БД, сначала определить её, различия схем и наличие нужных данных; переносить данные только по безопасному плану, не удаляя ни исходную, ни целевую базу. Тесты по-прежнему работают в отдельной тестовой БД.

8.5. Проверка фактического подключения, обязательная для Codex
Подключение PostgreSQL в окне Database IntelliJ и datasource запущенного Spring Boot приложения — независимые настройки. Наличие подключения в IDE не доказывает, что приложение использует ту же БД.

Просмотреть application.properties, YAML, profile-specific файлы, активные профили, параметры запуска, переменные SPRING_DATASOURCE_*, IDE Run Configuration и существующие deployment-настройки. Выявить, что реально переопределяет datasource. Пароли и токены не выводить.
Через тот же DataSource, которым пользуются JPA-репозитории приложения, выполнить read-only проверку:
SELECT current_database(), current_schema(), current_user,
       inet_server_addr(), inet_server_port();
SHOW search_path;
Сверить результат: database real_mobil_shop_sayt, schema public, согласованный пользователь и локальный сервер. Указать профиль и безопасный адрес без секретов. Проверка только через отдельную консоль IntelliJ недостаточна.
В локальном режиме сохранить один явно тестовый товар через приложение и подтвердить его появление в этой же БД/схеме в IntelliJ. Не использовать реальный телефон/заявку; тестовую запись затем убрать штатным способом. Не включать проверочный SQL или открытый диагностический endpoint в публичный production API.
Записать в STATUS факт подключения, способ проверки и результат. Если доступа к Windows/БД нет, указать BLOCKED и конкретный недостающий доступ; не сообщать «подключено» по одному содержимому properties.
localhost всегда относится к среде запущенного процесса. Для Codex в облаке или приложения в контейнере это не автоматически компьютер владельца. Не открывать порт PostgreSQL всему интернету ради подключения; использовать локальный запуск или согласованный защищённый доступ.

Успех создания — 201, повтор идемпотентного запроса — тот же логический результат. 11. Безопасность приложения
SEC-01. Вход и сессии
Spring Security обязателен. Для браузерного приложения на одном домене использовать серверные сессии с cookie Secure, HttpOnly, SameSite=Lax, подходящими Path и сроком. Идентификатор сессии обновляется после входа; logout — POST с CSRF и инвалидированием. Токены доступа не хранить в localStorage.

Предлагаемые таймауты админа: 30 минут бездействия и абсолютный срок 12 часов; проверять оба ограничения. При смене роли, отключении и сбросе пароля отозвать сессии. Для масштабирования допускается Spring Session JDBC; не полагаться на память одного процесса при нескольких backend-экземплярах.

Пароли хешировать адаптивным алгоритмом через PasswordEncoder с параметрами, проверенными на сервере. Минимум 12 символов, разрешены длинные парольные фразы; не обрезать молча. Лимит длины и выбранный алгоритм должны быть согласованы. Нет логирования пароля, открытого хранения или собственного «шифрования».

SEC-02. CSRF, CORS и права
Не отключать CSRF глобально ради работы React. Токен защищает login, logout, заявку и административные изменения. Настроить штатную SPA-интеграцию и получение нового токена после входа/выхода. Анонимный просмотр каталога не создаёт сессию на каждом GET; CSRF получать при открытии формы/входе. Endpoint токена не кешируется, ограничен от злоупотреблений.

Production работает same-origin; CORS при необходимости только с конкретными разрешёнными origins, без * с credentials. CORS не заменяет авторизацию. Проверка ролей на URL и сервисных операциях; негативные тесты подмены ID и полей.

SEC-03. Данные, контент и файлы
Параметризованные запросы JPA, запрет конкатенации SQL из ввода, allowlist сортировки.
Вывод контента с экранированием; в v1 описания plain text, без произвольного HTML.
CSP, запрет встраивания админки, nosniff, корректная Referrer-Policy; HSTS после проверки HTTPS.
Фото: до 8 файлов на модель, до 5 MiB каждый, суммарно до 40 MiB на запрос; лимит декодированного изображения, например 25 мегапикселей.
Проверять реальный формат и успешное декодирование; разрешить JPEG/PNG/WebP; SVG, HTML и исполняемые файлы не принимать.
Перекодировать изображения, удалить метаданные, создавать ограниченные размеры; число параллельных конвертаций ограничено.
Случайные storage keys, отсутствие исполнения, защита обхода путей. Не скачивать произвольные URL от администратора сервером.
Имена/телефоны не попадают в URL, аналитику, общие access-логи и публичный CDN-кеш.
SEC-04. Секреты и инфраструктурный доступ
Секреты через environment/секрет-хранилище; в репозитории только .env.example без реальных значений. Spring Boot должен явно получать конфигурацию; наличие файла .env само по себе не считается настройкой. Runtime-пользователь БД имеет минимальные права; роль миграций отдельно, где позволяет эксплуатация. БД слушает private network/localhost, не публичный интерфейс.

Actuator, метрики, технические страницы и подробный health не открывать всем. Внешний health отдаёт только минимальный статус, если необходим. SSH/управление ограничить. Сканирование секретов и зависимостей — часть CI. Нет неустранённых известных применимых critical/high уязвимостей при выпуске.

SEC-05. Персональные данные
Перед запуском владелец задаёт достоверные сведения о магазине, текст обработки данных и период хранения с учётом своей юрисдикции. Не выдавать автоматически сгенерированный текст за юридически проверенный.

Технический default для обсуждения: обезличивать имя/телефон через 180 дней после закрытия заявки, сохранять неперсональные агрегаты; срок конфигурируется. Открытые заявки старше срока помечаются OWNER для решения. Реализовать контролируемое удаление/обезличивание по обращению, включая отложенные уведомления; документировать срок выхода данных из резервных копий. До production период и текст должны быть определены.

12. Защита от DoS/DDoS и перегрузки
DOS-01. Уровни защиты
Хостинг/сетевой провайдер с противодействием объёмным сетевым атакам.
CDN/reverse proxy/WAF перед публичным сайтом с доступными на выбранном тарифе правилами L7 и фильтрацией ботов.
Закрытый origin: доступ HTTP(S) только через доверенный proxy/tunnel или allowlist; проверить отдельно IPv4 и IPv6, альтернативные порты и DNS.
Ограничения приложения: запросы, соединения, очереди, фоновые задания, размеры ввода, таймауты.
Мониторинг, оповещения и инструкция реакции.
Провайдер выбирается на этапе развёртывания. Cloudflare — пример возможного сервиса, а не оплаченный или уже настроенный компонент. Проверить фактические функции выбранного плана. Spring Security/WAF по отдельности не обеспечивают абсолютной DDoS-защиты. Не обещать выживание при любой мощности атаки.

DOS-02. Управление частотой запросов
Предварительные лимиты для настройки, затем проверить на NAT-сценарии и нагрузке:

Операция	Стартовое правило
Неудачный вход	До 5 попыток за 15 минут на логин с задержкой и до 30 на источник; без бессрочной блокировки аккаунта
Создание заявки	До 3 новых заявок за 10 минут на клиентский маркер и до 5 на нормализованный телефон за час; отдельный более мягкий лимит источника
Поиск	До 30 запросов в минуту на клиентский маркер, короткий burst до 10
Чтение каталога	Мягкое ограничение на краю по наблюдаемому поведению; не ограничивать всю мобильную сеть одним низким IP-порогом
Админские загрузки фото	Ограничение размера, частоты и параллельной обработки
Маркер клиента не является доказательством личности; использовать совокупность сигналов. Телефон для счётчика можно представлять HMAC, не логировать открыто. Повтор идемпотентного запроса не создаёт новый лид и учитывается отдельно от новых заявок. При подозрительной активности допустима дополнительная проверка, а не CAPTCHA для каждого клиента.

Настройки не зашивать в бизнес-код. При нескольких экземплярах лимиты должны быть общими на внешнем proxy/специализированном хранилище либо иметь доказанную согласованность. Не записывать счётчик каждого публичного GET в PostgreSQL, создавая новый источник DoS.

DOS-03. Ограничение ресурсов
Обычный JSON-запрос до 64 KiB; multipart имеет отдельные лимиты.
Размеры строк, массивов ID, страниц и фильтров ограничены до обращения к БД.
Таймауты чтения заголовков/тела на proxy защищают от медленных соединений.
Поиск и запросы БД имеют конечный deadline; контроль длительных транзакций.
Hikari pool, потоки, буферы, фоновые отправки и image processing ограничены; нет неограниченных очередей.
429/503 возвращаются контролируемо с Retry-After; не падать из-за исчерпания памяти.
Forwarded/IP-заголовки принимать только от доверенных proxy, чтобы клиент не обходил лимит поддельным IP.
Не кешировать персональные/административные ответы; для публичного кеша нормализовать допустимые query-параметры и не создавать бесконечные ключи по произвольному вводу.
DOS-04. Проверка и пределы
Проверять лимиты, подмену forwarded headers, большие payload, медленные запросы, отказ зависимостей и закрытие origin на собственном тестовом стенде. Объёмные сетевые DDoS-испытания не выполнять против чужих систем или без разрешения хостинга. Обычный нагрузочный тест на 2 000 клиентов не является доказательством защиты от распределённой сетевой атаки.

13. Производительность и нагрузочные критерии
PERF-01. Пользовательская скорость
Цели реальных посещений на 75-м процентиле отдельно для мобильных и desktop: LCP ≤ 2.5 с, INP ≤ 200 мс, CLS ≤ 0.1. До появления реальных данных использовать воспроизводимые лабораторные прогоны на согласованном среднем Android, iPhone и desktop с зафиксированной сетью. Не выдавать Lighthouse score или лабораторный TBT за доказанный пользовательский INP.

Оптимизировать responsive images, WebP/AVIF при поддержке, явные размеры, lazy-loading изображений ниже первого экрана. Главное изображение не откладывать без причины. Начальная публичная JS-загрузка — ориентир ≤ 200 KiB gzip, CSS ≤ 50 KiB gzip; админский код и тяжёлые библиотеки загружать отдельно. Отклонение фиксируется и оценивается по реальным измерениям. Не встраивать тяжёлые карты/видео на главный экран.

PERF-02. Определение нагрузки
«Одновременно активные посетители» — люди, которые остаются на сайте и выполняют действия с паузами, а не 2 000 HTTP-запросов в одну миллисекунду. Зафиксировать две модели испытаний:

Закрытая модель: 1 000, затем 2 000 виртуальных посетителей, действия примерно раз в 10 секунд, с реалистичными случайными паузами. Реально достигнутый RPS указать в отчёте.
Открытая модель: независимо поддерживаемые 100 и 200 динамических HTTP-запросов/с, чтобы замедление сервера не снижало незаметно интенсивность теста.
Профиль 200 запросов/с: 45% выдача каталога/скидок, 25% карточка, 20% поиск/цена, 8% публичные контакты/настройки/категории, 1% CSRF-токен формы, 1% валидные заявки с уникальными тестовыми данными. Избранное меняется локально; обновление его карточек включить в чтение каталога. Дополнительно 10 администраторов просматривают заявки и периодически редактируют товары. Статические файлы/изображения измеряются отдельным браузерным/edge-профилем и учитываются в общем трафике, но не смешиваются с RPS API.

Использовать 10 000 моделей, 20 000 комплектаций, 40 000 изображений по метаданным и реалистичную историю минимум 100 000 заявок. Все записи и номера синтетические. Запросы распределяются по популярным и редким товарам, а не одному кешированному URL. Если реальный план каталога существенно меньше/больше, сохранить этот эталон либо явно пересогласовать размер.

PERF-03. Условия приёмки
На заявленной конфигурации production-подобного стенда при 2 000 посетителей и отдельно при 200 динамических запросов/с:

Метрика	Требование
GET каталога/поиска/товара	p95 ≤ 500 мс, p99 ≤ 1 500 мс
POST заявки до commit и ответа	p95 ≤ 1 000 мс, p99 ≤ 2 000 мс
Серверные ошибки/таймауты	Менее 0.1% валидных запросов
Неожиданные отказы валидным клиентам	Менее 0.1%, включая ошибочные 429; не скрывать их из отчёта
Сохранность	Ни одной потерянной подтверждённой заявки
Повторы	Один лид на один idempotency key
Ресурсы	Нет OOM, перезапусков, утечки памяти или бесконечного роста очередей
Админ-панель	Сохраняет работоспособность и приём новых заявок
API-задержки измеряются от нагрузочного генератора через production-подобный вход до полного ответа, отдельно от загрузки изображений и браузерного рендера. Генератор не запускается на сервере приложения; его мощности, регион и RTT фиксируются. Для мобильного UX отдельно учитывается сеть пользователя.

Нельзя исключать законные заявки ради красивых процентов. Ожидаемые отказы заведомо невалидным/атакующим запросам считаются отдельно в защитных сценариях. При ложном срабатывании защиты на обычного клиента это дефект.

PERF-04. Набор прогонов
Smoke на малой нагрузке и проверка целостности сценариев.
Разогрев 10 минут; тест 1 000 посетителей не менее 30 минут.
Тест 2 000 посетителей не менее 60 минут.
Отдельная открытая модель 200 RPS не менее 30 минут.
Длительный тест 1 000 посетителей не менее 4 часов.
Резкий рост 500 → 2 000 и восстановление после него; отдельно холодный кеш без подмены обычных результатов.
Ступени 2 500, 3 000 и далее по ресурсам стенда — найти предел. При выходе за SLO зафиксировать предел, причину и план расширения, а не обещать бесконечную нагрузку.
Проверка сбоя Telegram и перезапуска backend: подтверждённые заявки остаются, outbox восстанавливается.
NAT-профиль: много независимых обычных посетителей с одним внешним IP; защита не блокирует их всех автоматически.
Отчёт: commit, дата, версии, размеры данных, CPU/RAM/диск/канал каждого узла, параметры JVM/DB/pool/cache, конфигурация edge/WAF, число пользователей, предложенный и достигнутый RPS, p50/p95/p99, 4xx/5xx/429, ошибки, CPU/память/GC/DB wait, исходные результаты и вывод PASS/FAIL/BLOCKED. Нельзя писать PASS без выполненного прогона.

PERF-05. Кеш и масштабирование
Статика с хешами — длительный cache-control; публичные каталоги/настройки — ограниченный TTL и инвалидация после изменений. Цена, публикация и наличие становятся актуальными не позднее 60 секунд, но POST заявки всегда проверяет первичные данные. При срочном скрытии/отключении кеш инвалидируется сразу; скрытые данные не продолжают выдаваться из старого кеша.

Не создавать сессию для каждого анонимного просмотра. Оптимизировать SQL и изображения до увеличения числа серверов. Сначала измерить один backend; затем при необходимости увеличить ресурсы или число экземпляров. При нескольких экземплярах обеспечить общие сессии, согласованные лимиты, общие фото, корректную обработку outbox и инвалидацию кеша. Не назначать заранее неподтверждённую конфигурацию сервера как гарантированно достаточную.

14. Надёжность и эксплуатация
OPS-01. Окружения
Раздельные local/test/staging/production, разные базы/секреты. Нагрузочные и разрушительные тесты не используют real_mobil_shop_sayt с реальными данными. В production запрещены демонстрационные админы и синтетические заявки. Есть readiness/liveness, graceful shutdown и автоматический перезапуск процесса средствами хостинга.

Frontend и API публикуются одним origin с корректной маршрутизацией. Фото не хранятся внутри временного каталога приложения. Смена сборки не удаляет медиа и конфигурацию.

OPS-02. Мониторинг
Метрики: HTTP latency/errors/RPS, активные запросы, JVM/GC, pool DB, медленные запросы, disk, outbox backlog/failed, возраст последнего успешного backup. Оповещения о недоступности, росте 5xx, перегрузке, подозрительном трафике, очереди уведомлений и неуспешной резервной копии.

Первоначальные пороги документировать и откалибровать: например 5xx > 1% за 5 минут при достаточном трафике, CPU > 85% 10 минут, свободный диск < 15%, oldest pending notification > 5 минут. Получатель технических тревог задаётся отдельно от публичного телефона магазина.

Эксплуатационная цель после запуска — доступность ≥ 99.5% в месяц с указанной методикой расчёта, учитывающей незапланированные простои. За первые минуты после публикации этот показатель не считается доказанным.

OPS-03. Резервные копии и восстановление
Предлагаемые цели: RPO ≤ 1 часа, RTO ≤ 4 часов. Для достижения RPO недостаточно только ежедневной копии: нужны подходящий managed backup/PITR либо архивирование WAL вместе с базовыми копиями. Медиа и конфигурация также защищаются; секреты хранятся отдельно и безопасно.

Копии зашифрованы, находятся отдельно от сервера, доступны ограниченному кругу, имеют срок хранения (стартовый ориентир 30 дней). До выпуска выполнить восстановление на отдельной базе и сверку заявок/медиа, записать фактические RPO/RTO. Если инфраструктура не обеспечивает цели, статус BLOCKED/требуется решение, а не фиктивный PASS.

OPS-04. Выпуск и откат
Перед миграцией проверить backup и совместимость; по возможности применять добавочные миграции. Зафиксировать версию приложения и схему. Откат приложения не означает автоматический откат данных: использовать совместимый предыдущий релиз или отдельный план восстановления. Выполнить репетицию staging-отката.

Инструкция инцидента: обнаружение → ограничение ущерба → восстановление → проверка целостности → разбор причины. Для DDoS: проверить edge/origin, включить согласованные усиленные правила, ограничить дорогие операции, уведомить провайдера, контролировать ложные блокировки. Не отключать безопасность целиком ради восстановления.

15. SEO и содержимое
В v1 обязательны понятные URL, заголовки страниц, базовые метаданные, canonical, robots и sitemap только опубликованных товаров. Админка/избранное/формы не должны попадать в индекс. Скрытые страницы не включаются в sitemap; статические и API-404 согласованы с маршрутизацией.

React SPA без дополнительного рендеринга не гарантирует идеальную индексацию и карточки ссылок во всех сервисах. До G1 определить важность органического поиска. Если нужен полноценный SEO-каталог, принять отдельное решение о prerender/SSG публичных страниц с обновлением после изменения товара; бизнес-API остаётся Java. Не добавлять Node.js бизнес-backend. Без решения по этому пункту не заявлять «полное SEO».

Фотографии и тексты предоставляет магазин или использует материалы с подходящими правами. Нельзя автоматически копировать базы/описания конкурентов. Для демонстрации использовать явно помеченные тестовые данные без выдуманных реальных цен и характеристик.

19. Definition of Done и финальная приёмка
Задача DONE, когда реализовано поведение, выполнены соответствующие тесты, проверены негативные случаи, обновлены миграции/API/инструкции, нет секретов и неразобранных критичных замечаний. Скриншот интерфейса не доказывает работающий backend, а успешная сборка не доказывает нагрузку.

Релиз готов, когда:

Все обязательные FR реализованы и пройдены применимые AT.
Реальный backend использует Spring Boot/JPA/Hibernate/PostgreSQL; mock API не остаётся источником production-данных.
Пройдены проверки ролей, сессий, CSRF и защиты клиентских данных.
Достигнуты целевые нагрузочные показатели на указанной инфраструктуре; запас выше 2 000 измерен и честно описан.
Настроены edge/WAF, origin, TLS, мониторинг и backup/restore; нет необоснованного утверждения об абсолютной DDoS-защите.
