## Telegram

Канал не настроен в доступной конфигурации: нет TELEGRAM_BOT_TOKEN и TELEGRAM_CHAT_ID. Внутренний счётчик работает независимо. Передача публичного Telegram-контакта магазина не включает доставку боту.

Владелец задаёт оба секрета в окружении процесса/секрет-хранилище, затем перезапускает приложение. Бот должен иметь доступ к выбранному личному чату/закрытой группе. Через витрину отправить одну явно тестовую заявку и проверить тот же номер в панели и группе. Не использовать рабочую группу в нагрузочных тестах.

В OWNER → Уведомления видны состояние канала, очередь, попытки и безопасный код ошибки. 401/403 требуют проверки токена/прав/получателя локально; 429 учитывает parameters.retry_after и Retry-After. Повтор FAILED доступен владельцу. Outbox появляется только для заявок, созданных при включённом канале; старые заявки автоматически в Telegram не рассылаются.

Доставка считается успешной только при HTTP 200 и ok=true. Ответ ограничен 64 KiB, запрос — 6 с. Тело запроса и ответ с контактами не записываются в логи. Сообщение отправляется обычным текстом без parse_mode. После сетевой неопределённости возможен дубль сообщения с тем же номером; новый лид не создаётся. Документация протокола — [Telegram Bot API](https://core.telegram.org/bots/api#making-requests), [retry_after](https://core.telegram.org/bots/api#responseparameters).

## Защита и инфраструктура

Для deployment подготовлены application-production.properties и deploy/nginx.conf.example. Это непроверенный на внешнем стенде шаблон, а не работающий WAF. Профиль production требует DB_URL/DB_USER/DB_PASSWORD и связывает приложение с loopback; локальные файлы не меняет.

Proxy должен перезаписывать forwarded headers, доверие Tomcat ограничено локальным proxy. При CDN реальные адреса и заголовок клиента настраиваются по текущей документации провайдера. Firewall закрывает прямой origin на IPv4, IPv6 и других портах. management/PostgreSQL остаются приватными. Проверить обход из внешней сети и nginx -t перед выпуском.

Лимиты на аккаунт, сессию и телефон остаются включены. Для production предусмотрены грубые потолки IP 3000 заявок/10 мин и 12000 поисков/мин, чтобы один общий NAT не исчерпывал прежние 180/1200 для всех пользователей. Эти значения требуют проверки NAT-профилем и настройки под фактический трафик. Подмена IP, ротация сессий и объёмные атаки требуют edge/WAF и защиты провайдера.

Hikari ограничен 12 соединениями (DB_POOL_SIZE), SQL timeout 4 с, получение соединения 3 с, Tomcat 80 потоков/100 ожидающих соединений. JSON 64 KiB, загрузки отдельно ограничены. Новые updates/read ограничены по actorId 120/мин, поэтому один сотрудник не блокирует других за общим IP.

Текущая поставка рассчитана на один backend. Для нескольких экземпляров сначала нужны согласованные сессии и лимиты, отдельная проверка отзыва сессий и нагрузки. Не включать несколько экземпляров с локальными счётчиками как доказанную защищённую конфигурацию.
