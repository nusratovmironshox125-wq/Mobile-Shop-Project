4. FIX-01 — SOLID и архитектура
Организуй backend по понятным пакетам в существующем корневом package:

Пакет	Ответственность
config	Настройки приложения, Spring Security и интеграций
controller	HTTP-маршруты, входные DTO, HTTP-ответы
service	Бизнес-сценарии, правила, транзакции
repository	Spring Data JPA и запросы к PostgreSQL
entity	JPA-сущности и связи
dto	Входные и выходные модели API
mapper	Преобразования DTO/Entity без скрытых запросов к БД
exception	Предметные ошибки и единый обработчик
security	Текущий пользователь, аутентификация и проверки доступа
integration.telegram	Внешний adapter Telegram
Пакеты не являются доказательством SOLID сами по себе. Проверь реальные зависимости:

Controller вызывает service, не repository. Бизнес-логика не живёт в HTTP-контроллере.
Service владеет транзакцией и проверками правил; запросы к Telegram не держат открытую транзакцию БД.
Repository не формирует HTTP-ответы. Entity не отдаётся клиенту напрямую.
Используй constructor injection; не создавай зависимости вручную внутри бизнес-кода.
Выдели небольшие контракты на границах уведомлений/хранилища; изменение провайдера не меняет сохранение заявки.
Не создавай универсальный сервис с десятками несвязанных функций.
Не создавай интерфейс/Impl на каждый класс только ради названия SOLID; простые сервисы с одной реализацией могут быть конкретными.
Подстановочные реализации контрактов должны одинаково соблюдать поведение успеха/ошибки.
Рефакторинг не должен менять рабочие API и данные без обоснованной миграции.
Добавь архитектурные проверки действительно важных границ и регрессионные тесты. Не делай полную перепись работающего проекта.

5. FIX-02 и FIX-03 — заявки и заметные уведомления
5.1. Проверка цепочки
Проверь последовательно: frontend submit → security/CSRF → валидация → commit заявки → событие/outbox → административный API → обновление frontend → Telegram adapter при подключённом канале. В отчёте укажи, на каком участке был подтверждён дефект.

HTTP-успех клиенту возвращается после сохранения в PostgreSQL. Двойной клик/сетевой повтор не создаёт второй лид. Ошибка уведомления не отменяет заявку. Заявка содержит имя, телефон, модель, выбранную комплектацию, артикул и снимок цены.

5.2. Видимость в админ-панели
Сделай обязательными:

Счётчик непрочитанных возле раздела «Заявки», видимый на всех страницах панели, включая мобильное меню.
Выделение непрочитанных строк и понятную отметку «Новая».
Краткое всплывающее уведомление при поступлении новой заявки в открытой панели: номер, товар и действие «Открыть». Не показывай полный телефон в toast, если это не нужно.
Обновление списка и счётчика без ручной перезагрузки. Для активной вкладки при нормальной работе цель — не позже 15 секунд после commit.
После временного обрыва соединения или возврата во вкладку восстановление по данным сервера; событие не должно быть единственным источником истины.
Обозначение состояния связи, если обновление не работает. Не показывать старый ноль так, будто заявок точно нет.
Если действующий polling исправен, достаточно исправить его: ориентир каждые 10 секунд, только при видимой вкладке, с отменой старого запроса и задержкой при ошибках. Если уже используется SSE/WebSocket, проверь авторизацию, reconnect и добор пропущенных заявок; не заменяй транспорт без необходимости.

Не отправляй запрос обновления на каждый render. При logout останови обновление и очисти клиентский кеш предыдущего администратора. Вкладки одного аккаунта не должны порождать бесконечные дубли уведомлений; предусмотрена дедупликация по ID заявки/события.

5.3. Прочитано и обработано — разные состояния
NEW/CONTACTED/COMPLETED/CANCELLED — общий бизнес-статус заявки.
readAt — состояние просмотра конкретным администратором; хранится на сервере, а не только в localStorage.
Открытие заявки отмечает её прочитанной у текущего администратора после успешной загрузки; не меняет автоматически статус на CONTACTED.
Прочтение одним администратором не скрывает непрочитанную заявку у другого.
Счётчик учитывает все непрочитанные заявки, а не только текущие 10 строк и не только открытый фильтр.
Обновление списка само по себе не отмечает всё прочитанным.
Первый вход показывает накопленный счётчик/краткую сводку, а не десятки toast по каждой старой заявке.
Для новых администраторов принять простое правило: существующие доступные заявки считаются непрочитанными, пока они не просмотрены или явно не выполнено «Отметить все прочитанными». Если добавляешь массовую отметку, используй серверную границу по времени/ID, чтобы заявка, пришедшая параллельно, не оказалась случайно прочитанной.

Предпочтительная логическая модель: запись просмотра (adminId, leadId, readAt) с уникальностью пары или эквивалентная схема с тем же поведением. Бизнес-статусы и прочтение не смешивать.

5.4. Telegram
Если канал подключён, проверь получателя, разрешения, состояние отправщика и безопасные ответы Telegram API. Бот/закрытая группа администратора не равны публичному Telegram-контакту магазина.

Используй сохранённый outbox с повторными попытками, ограниченными таймаутами и восстановлением после перезапуска. Сообщение содержит номер заявки, имя, телефон, товар, комплектацию, артикул и цену. Данные экранируются; токен скрыт.

Если токена/получателя нет, исправь внутренние уведомления независимо и пометь реальную Telegram-доставку как BLOCKED. Не имитируй успех. Провайдерные тесты выполняй через adapter-заглушку; реальное контрольное сообщение отправляй только в настроенный владельцем канал с явно тестовыми данными. При сбое после отправки возможен повтор сообщения; один и тот же номер заявки позволяет определить дубль, новый лид не создаётся.

6. FIX-04 — комплектации строго по категории
При выборе категории «Телефоны» показываются только общие поля и поля телефона. При выборе «Ноутбуки» — только общие поля и поля ноутбука. Устрани смешение при создании, редактировании и публичном просмотре.

Группа	Поля
Общие	Название/бренд на уровне модели; у варианта артикул, цена, наличие, цвет, скидка, рассрочка
Телефон	RAM при применимости, встроенная память, экран, процессор, камеры, аккумулятор, SIM/eSIM, ОС
Ноутбук	CPU, GPU, RAM, накопитель и его тип, экран, ОС, вес; дополнительные ноутбучные параметры при наличии
Некоторые характеристики общие по смыслу. Не дублируй их в несовместимых формах. Например, у телефона тоже есть процессор, но поля дискретной видеокарты ноутбука ему показывать не нужно.

Технические правила:

Тип PHONE/LAPTOP задаётся категорией или её схемой на backend. Не определяй его сравнением отображаемого названия «Телефоны», которое меняется при переводе/переименовании.
В форме сначала выбирается категория. Затем отображаются связанные поля с правильной валидацией.
При смене категории нового черновика несовместимые введённые поля очищаются после предупреждения, если есть что потерять. Скрытые поля не отправляются.
У существующего товара с комплектациями запрети прямую смену технического типа до явного сценария преобразования. Не удаляй характеристики молча. Переименование/изменение категории того же типа может быть разрешено.
Backend проверяет согласованность category/type/DTO и отклоняет чужие поля с понятной ошибкой 400. Только скрыть поля CSS недостаточно.
Смена категории, локали и повторное открытие формы не возвращают старые поля через сохранённое состояние.
Несколько реальных комплектаций создаются как отдельные варианты; не генерируй несуществующие комбинации автоматически.
Старые смешанные записи обследуй. Исправляй однозначные случаи миграцией с backup; неоднозначные пометь для ручной проверки, не угадывай и не удаляй данные.
7. FIX-05 — «Адрес страницы» / slug
Slug — часть URL страницы, например /products/samsung-galaxy-a55. Он не заменяет артикул комплектации и не обязан быть заметен покупателю отдельным полем.

Найди, используется ли текущее поле в маршрутах, ссылках карточек, API и sitemap. Укажи факт, а не предположение.
Обычному администратору не нужно вручную заполнять «Адрес страницы (например, model-x)» для сохранения товара. Убери поле из обязательной основной формы.
Если текущая маршрутизация использует slug, генерируй его автоматически из модели; обеспечь уникальность ограничением БД и безопасной обработкой конфликтов. Для неподдерживаемого/пустого после нормализации названия — стабильный fallback на ID.
Если текущий сайт уже использует стабильный ID URL и slug нигде не применяется, удали неработающее поле из интерфейса и DTO, не ломая существующие ссылки. Не создавай фиктивный slug только ради наличия поля.
Если полезно, покажи read-only «Ссылка на товар» с кнопками открыть/скопировать. Ссылка должна действительно вести на товар.
Переименование товара не должно автоматически ломать его опубликованную ссылку. При необходимости изменения URL используй документированную совместимость/редирект.
Скрытые/архивные товары через прямую ссылку не обходят правила публикации.
Выбор ветки зависит от фактической архитектуры; зафиксируй его в DECISIONS и актуализируй OpenAPI/ТЗ. Не удаляй колонку из БД до проверки её использования и миграции.

8. FIX-06 — понятный артикул/SKU
SKU — код конкретной комплектации для сотрудников и поиска. Один телефон 128 ГБ чёрный и тот же телефон 256 ГБ белый имеют разные SKU.

В админке подпись «Артикул товара (SKU)», короткая подсказка о назначении.
При создании можно автоматически предложить уникальный код; разрешить ввод собственного кода при проверке уникальности. Уникальность обеспечивается также БД, включая одновременное создание.
По артикулу работает поиск товара/комплектации в админке. Сопоставление регистра и пробелов определено явно и одинаково при сохранении/поиске.
Артикул входит в заявку, Telegram-сообщение и ссылку из журнала на объект.
Клиент не вводит артикул вручную. В публичных подробностях допустима вторичная подпись «Артикул», но это не заголовок товара.
SKU не считается секретом и не является механизмом контроля доступа.
Не менять существующие артикулы массово при рефакторинге и не переиспользовать их для других вариантов. Историческая заявка хранит исходный артикул.
9. FIX-07 — характеристики с понятными подписями
Сейчас пользователь видит отдельное значение вроде «чёрный», не понимая его смысла. Исправь представление на странице товара, в выборе комплектации, форме заявки, административном просмотре и уведомлениях.

Правильный пример для телефона:

Цвет: чёрный.
Оперативная память: 8 ГБ.
Встроенная память: 256 ГБ.
Для ноутбука:

Процессор: Intel Core i5 …
Оперативная память: 16 ГБ.
Накопитель: SSD, 512 ГБ.
Видеокарта: название конкретной модели, если указано.
Это примеры отображения, не реальные характеристики товаров магазина.

Требования:

У каждой группы выбора есть видимая подпись, например «Цвет», а у выбранного варианта понятная сводка. Кнопки внутри подписанной группы могут содержать только значение.
Подписи интерфейса переводятся RU/UZ; введённые администратором значения автоматически не переводятся. Текст «чёрный» может остаться русским в узбекском интерфейсе согласно исходному требованию.
Единицы измерения отображаются один раз: не «256 ГБ ГБ». Типизированные значения форматируются централизованно.
Не показывать null/undefined/пустые параметры и чужие характеристики категории. Значение 0 не считать пустым без проверки смысла поля.
Цвет можно дополнить образцом, но текст сохраняется для понятности и доступности.
Страница, заявка и сообщение должны описывать одну и ту же выбранную комплектацию. При смене варианта синхронно обновляются цена, наличие, артикул и подписи.
Если существующие данные — строки с уже встроенными единицами, обработай их совместимо или мигрируй проверяемо; не исправляй только один экран.
10. FIX-08 — журнал действий по username
Журнал должен показывать бизнес-действия сотрудников, а не просто уровень логирования INFO.

Пример строки:

admin_ali изменил цену комплектации SAM-025: 3 500 000 → 3 300 000 сум. 11.11.2026, 14:20.

Пример иллюстративный; не добавляй его как реальное событие.

Поля события: eventId, actorId, username на момент действия, роль, код действия, тип/ID объекта, артикул/имя объекта при наличии, изменённые разрешённые поля «до/после», timestamp UTC, correlationId и результат при применимости.

Actor берётся из аутентифицированного пользователя Spring Security, никогда из присланного клиентом username/`adminId`.
Храни стабильный actorId и снимок username: переименование/отключение администратора не стирает историю.
Для фоновой операции явно SYSTEM, без выдуманного username человека.
Не записывай пароли, хеши, токены, cookie и полные клиентские контакты. Для изменения пароля достаточно «Пароль изменён»; значения не сохраняются в diff.
Записывай создание/изменение/архивирование товара, комплектации, цены, скидки, наличие, настройки, категории, действия с администраторами и статусы заявок.
Успешное изменение и аудит должны быть согласованы транзакционно; при rollback не записывать событие как успешное. Неудачные попытки доступа учитываются отдельно как события безопасности.
Фильтры: username/администратор, действие, объект/артикул, даты. Сортировка по времени с ID для стабильного порядка. Пагинация по 10.
В интерфейсе: время, username, понятное действие, объект, раскрываемые детали изменений. Коды вроде PRODUCT_UPDATED переводятся в человеческий текст RU/UZ.
Доступ к общему журналу по исходной матрице только OWNER; обычный ADMIN не получает право просмотра всех действий автоматически.
Для старых записей восстанавливай автора только по имеющимся достоверным связям. Если автора определить нельзя, показать «Автор не сохранён», не назначать текущего администратора.
Журнал недоступен для редактирования/удаления через обычные endpoints панели.
11. FIX-09 — пагинация строго по 10
Основное правило: один экран списка — максимум 10 записей; последняя страница содержит остаток. Не загружай весь серверный список и не называй разрезание массива в браузере серверной пагинацией.

Применить:

Список	Правило
Главная/каталог, телефоны, ноутбуки	10 моделей на страницу, не 10 комплектаций
Скидки	10 подходящих моделей
Товары в админке	10 товаров
Заявки в админке	10 заявок
Журнал действий	10 событий
Администраторы, категории, отдельный список доставки уведомлений	Если это полноценный список, также 10 записей
Избранное	10 моделей; локальная пагинация допустима для ограниченного списка ID в браузере, цены/видимость актуализируются сервером
Селекторы цвета/памяти, навигационные ссылки и форма комплектаций не превращаются в таблицы с пагинацией. Если главная содержит отдельный небольшой промоблок, правило относится к основному каталогу, а не к навигации.

Контракт:

API списков использует page от 0, size=10; UI показывает страницы от 1. Если текущий API нумерует иначе, сохрани совместимость через явное преобразование и обнови документацию.
По умолчанию 10; переданное другое значение размера для этих списков отклоняй с 400 или нормализуй к 10. Выбери единое поведение и зафиксируй его, без разных правил на разных экранах.
Ответ содержит items, page, size, totalElements, totalPages и достаточные признаки перехода назад/вперёд. Фактические имена можно сохранить, если они уже стандартизированы в проекте.
Поиск/фильтры применяются ко всей выборке в БД до LIMIT/OFFSET. После изменения поиска/категории/цены/сортировки открывается первая страница.
При JOIN с несколькими вариантами один товар не дублируется. totalElements считает модели, удовлетворяющие фильтру, а не строки JOIN.
В URL сохраняются страница, фильтры и сортировка. Перезагрузка, назад/вперёд браузера и возврат из товара корректны.
Кнопки «Назад/Далее», номер текущей страницы и диапазон «11–20 из 37». На телефоне управление компактное, без горизонтального overflow.
Пустой список — «Ничего не найдено», без «Страница 1 из 0» и активных несуществующих переходов.
При удалении/архивировании последней записи на странице перейти на последнюю существующую страницу. Некорректный page отклоняется безопасно; для page за пределами — пустой ответ с корректными totals и нормализация UI без зацикливания.
Стабильная сортировка с вторичным ключом ID. При изменяющемся списке новая заявка не должна внезапно переключать администратора с третьей страницы на первую: обнови счётчик/баннер «Есть новые заявки» и предложи открыть их.
Не включай публичную регистрацию пользователя и не создавай сессию на каждый запрос каталога ради пагинации.
12. FIX-10 — безопасность и производительность
12.1. Проверка Spring Security
Подтверди фактическую защиту маршрутов, а не только наличие зависимости:

Публичный каталог доступен без входа; административные действия требуют входа и роли.
Неавторизованный пользователь не получает заявки, телефоны, аудит, настройки секретов и не меняет товары.
ADMIN не создаёт OWNER и не повышает свою роль; отключение админа отзывает его сессии.
При cookie/session-аутентификации CSRF остаётся включённым и корректно работает с React; не отключай его ради устранения ошибки уведомлений.
Безопасные cookie, HTTPS production, адаптивное хеширование паролей, ограничение попыток входа.
Параметризованные запросы, allowlist сортировки, экранирование XSS, проверки DTO и файлов.
SQL и stack trace не уходят клиенту. Секреты/персональные данные не попадают в обычные логи.
Публичный кеш не содержит административных ответов или данных одного администратора для другого.
12.2. DoS/DDoS
Проверь и исправь ограничения размера запросов, длительности обработки, частоты входа/поиска/заявок, пулов соединений, фоновых задач и очередей. Защита по IP не должна автоматически блокировать всех клиентов одной мобильной сети. Счётчики уведомлений и новые endpoints прочтения тоже защищены и ограничены.

На инфраструктурном уровне требуются edge/CDN/WAF, подходящая защита провайдера и закрытие прямого origin, включая обход через IPv6/другие порты. При нескольких backend-экземплярах лимиты и сессии должны работать согласованно.

Если инфраструктура ещё не предоставлена, подготовь конфигурацию/инструкции и отметь внешнюю защиту как не проверенную. Локальный rate limiter не доказывает защиту от объёмного DDoS. Никаких обещаний абсолютной защиты. Испытания только на своём разрешённом стенде, без атак на сторонние сервисы.

12.3. Нагрузочная проверка
Не обещай «вообще без лагов» без условий измерения. Минимум: 1 000 одновременно активных клиентов; целевой уровень основного ТЗ — 2 000. Сохрани раздельную проверку реальных пользовательских пауз и фиксированной интенсивности запросов.

Профиль: просмотр каталога и страниц, поиск, цена/скидки, отправка заявок; дополнительно активные администраторы получают уведомления, открывают заявки, листают журнал и меняют товары. Не подменяй нагрузку запросами только к одному закешированному URL.

1 000 виртуальных посетителей с действиями примерно раз в 10 секунд: разогрев и не менее 30 минут стабильной нагрузки.
Отдельно открытая модель 100 динамических запросов/с не менее 30 минут, чтобы замедление не снижало незаметно нагрузку.
После успешной базовой проверки — 2 000 посетителей/200 запросов/с и длительные/пиковые сценарии основного ТЗ на подходящем стенде.
Репрезентативные синтетические данные по основному ТЗ, отдельная тестовая PostgreSQL. Нагрузочный генератор работает отдельно от приложения.
Не отправлять тысячи нагрузочных сообщений в реальную Telegram-группу: использовать тестовый adapter; одну реальную доставку проверить отдельно при наличии настройки.
Критерии под нагрузкой:

Метрика	Цель
Каталог, поиск, карточка	p95 ≤ 500 мс, p99 ≤ 1 500 мс
Сохранение заявки	p95 ≤ 1 с, p99 ≤ 2 с
Серверные ошибки/таймауты	< 0.1% валидных запросов
Неожиданные отказы обычным клиентам, включая 429	< 0.1%; не исключать из отчёта
Новая заявка в активной админ-панели	Не позднее 15 секунд при исправном соединении
Подтверждённые заявки	Ни одной потерянной; повтор не создаёт дубль
Ресурсы	Без OOM, перезапусков и неограниченного роста очередей
Проверить SQL/N+1, планы поиска и COUNT для пагинации, индексы, bounded connection pool, тяжёлые фото, лишние rerender и дублирующиеся polling-таймеры. Не добавлять Redis/микросервисы без доказанной необходимости.

В отчёте зафиксировать commit, конфигурацию серверов/БД/сети, размер данных, сценарий, длительность, предложенный/достигнутый RPS, p50/p95/p99, ошибки, CPU/RAM/GC/DB waits, исходные результаты. Если среды для 2 000 нет, базовый результат сдаётся отдельно, целевой тест — BLOCKED, а не PASS.

Мобильная скорость проверяется отдельно от API-нагрузки: медленная сеть, изображения, layout shifts, отзывчивость кнопок. Сохраняются цели основного ТЗ LCP/INP/CLS; лабораторная оценка не выдаётся за статистику реальных пользователей.
